# Concurrent HTTP + PostgreSQL benchmark — 2026-11-01

Windows 11 host with Intel Core i7-12700; API server and load client run together inside a Linux .NET 10.0.9 SDK container. PostgreSQL 18.1 runs in a separate container on the same dedicated Docker network. HTTP uses direct loopback with proxy disabled. Both registrations share the same NpgsqlDataSource.

Each scenario uses 10,000 timed requests, 256 concurrent warmup requests, eight tenants, and validates the returned tenant row and initial context tenant on every request. The pool retains at most 32 idle contexts; the Npgsql pool maximum is 64. Each context has 100 or 300 generated models; the request queries one table with one matching row. Fluent=true applies one table mapping override; it is not the every-entity Fluent stress workload from the older microbenchmark. The two rounds reverse scoped/pooled order. Load generator and server share CPU, and scenario durations and results vary substantially; this is not remote-network, sustained production, write, or transaction throughput.

## Pool-overflow stress

300 models, Fluent=true, 64 concurrent clients, 4 retained idle contexts, 10000 timed requests: 10659 requests/s, mean 5.915 ms, P95 13.315 ms, P99 22.695 ms; errors 0, tenant leaks 0, dirty-state detections 0.

The Windows-host run that used the system proxy encountered exhausted ephemeral ports and was discarded. The results above use Linux containers and direct loopback; no operating-system network settings were changed.

## Optional pool-return hook isolation check

After switching the API benchmark context to override `OnPoolReturn()` instead of implementing `IPooledDbContext`, a separate run used Windows-hosted Kestrel with direct loopback HTTP and a dedicated PostgreSQL 18.1 Docker container. The 300-entity, Fluent-enabled case used 32 concurrent clients, 16 retained idle contexts, eight tenants, 256 warmup requests and 10,000 timed requests. Each response checked its initial tenant state, expected tenant and database row. Result: 0 request errors, 0 cross-tenant row mismatches and 0 stale-state detections. This is a correctness check of an explicitly overridden hook, not proof that the default empty hook resets user-owned state.
